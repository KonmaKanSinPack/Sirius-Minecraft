## 二、设计决策（含理由）

1. **匹配集 = 实际挖掉的方块 id + block_ids 纯 id 项**：logs 类挖啥掉啥（oak_log→
   oak_log），用 `nearest["block"]`（filter 查询已解析出的注册名）比 block_ids 更
   准——后者可能是 `#logs`（tag 无法在 item 注册名上展开，无 item tag 查询通道，
   保守忽略，全 tag 调用退化为只匹配实挖 id）。**匹配不上的绝对不碰**：多人服上
   别人的掉落/树叶掉的树苗一律留给原主（礼仪），旧 jar（无 item 字段）同样保守不捡。
2. **"已拾取"判定 = 实体消失**（Numen 语义）：`before - after` 实体 uuid 集合差——
   谁捡的无关紧要（自己吸附/路过顺吸/别人抢走都算消失），且走位途中路过吸走的
   其他同家族掉落自然计入。走位后 `_settle_drops` 轮询 ≤3s：walk_to 在 ≤2 格
   （WALK_ARRIVE_DIST）即返回而 Baritone 还在收尾，给它时间走完最后 1 格。
3. **skip + 尝试上限双保险防死循环**：身旁 ≤1.2 格（Numen PICKUP_REACH_SQR=1.5
   开方）仍没吸上 → skip；>1.2 格没吸上 → 换最新坐标再走一次（#goto 收尾半径
   2 格可能停在 1.2-2.0 之间），两次后 skip。每轮有捡到或跳过即有进度，无进度
   或 20s 超时即收——不会对着同一个实体无限走。
4. **pickup 默认 True 的理由**：采集场景（"搜集云杉木 5 根"）要的就是物品本身，
   挖完不捡等于任务失败一半；挖通道/清地形的掉落物（圆石/泥土）反而拖慢节奏，
   由 VLM 按任务意图传 False——意图层决策留在 LLM，执行层下沉确定性代码（M3.5
   轮的既定架构方向）。
5. **schema 重导出核实为不适用**：collectBlock 是 brain 侧工具，参数 JSON 在
   tools.py 手写、不在 protocol TOOL_PARAMS/export_schema 范围；world.query 的
   item/count 是**响应侧**载荷（schema 只冻结 params）。协议无变化（仍 1.2），
   重跑导出只会 churn index.json 的 exported_at 时间戳，故未执行。
