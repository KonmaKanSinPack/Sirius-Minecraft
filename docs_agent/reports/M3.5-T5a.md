## 真机缺陷（Primitives 侧，本轮已修，287 单测全过）

### 缺陷 1：挖掘 hold 时长低于徒手破坏时间（8 段全空的根因）
- 现象：`DIG_CLICK_HOLD_MS=600` 时 dig_block 连续 8 段挖不掉 oak_log（走位/视线都正确）
- 根因：vanilla 机制松键后挖掘进度清零、跨段不累积；徒手 oak_log = hardness 2.0×1.5 = **3.0s** 连续按住（原注释"徒手/铁斧 0.3-0.6s"混淆了有斧速度）
- 修复：`DIG_CLICK_HOLD_MS` 600 → **3500**（`primitives.py` 常量 + 注释重写）；`test_dig_success` 断言改引用常量

### 缺陷 2：段循环不等 hold 完成就发下一段
- 现象：修复 1 后 collect 仍假失败——8 段 5.3s 跑完（每段只等 settle 0.4s）
- 根因：hold 的 RELEASE 由 bridge SCHEDULER 延迟调度，段循环 0.4s 后发下一段 PRESS 堆叠在按住中途，且上一段**迟到的 RELEASE 触发 stopAttack 清进度**
- 修复：段等待改为 `hold_ms/1000 + DIG_SETTLE`

### 缺陷 3：遮挡场景固定 3.5s 仍不够（递增 hold）
- 现象：树干高段 (11,66,26)（低段已挖光的最后一格，四周 decay 树叶环绕）8×3.5s 仍挖不掉；手动 8s hold 一次穿透
- 根因：视线先穿 k 格树叶（0.35s/格）再达树干，需 hold ≥ 0.35k+3.0s；固定 3.5s 只覆盖无遮挡
- 修复：hold 按段递增 `min(3500×n, 8000)`（新常量 `DIG_CLICK_HOLD_MAX_MS=8000`），`DIG_TIMEOUT` 40→75s；重跑 collect 3/3 PASS（11 段，83.2s）

## Java 侧 bug（需主管裁决，本轮按约束未动 jar/未重启游戏）

**world.query 的 cap 截断发生在距离排序之前**——违反 T1"truncated 时最近方块仍可信"契约：

- 无 filter（cap 512）铁证：range=4.0（count=438 未截断）能看到 3.71 格处的目标；range=5.5 起 count=512 截断后**同目标反而消失**（更近的方块被任意丢弃）
- filter 路径同样中招：`['#minecraft:logs','#minecraft:leaves']` range=8 截断时，距离第一的 (11,66,26)（filter=[oak_log] 各 range 一致命中且排第一）不在结果里
- 后果链：dig_block 的"已不存在"幂等路径把截断误判为真空 → collect_block 零挖掘 3 次假成功（"已挖到 3/3"但世界零变化）——本轮真机踩到的最隐蔽一环
- Python 侧防御（已入库）：`_query_blocks` 返回 `(blocks, 是否完整)`；`_block_at` 未命中**仅在未截断时可信**，截断时保守视为存在/还在（8 段上限兜底）；`_collect_block` 把 `nearest["block"]` 透传给 dig 的复核（filter 复核 + 可靠性判定双保险）
- 建议：Java 侧 T6 修复（截断应在距离排序后取前 N），修复前 Python 侧防御已可安全运行；probe 脚本 1a 的"距离升序"检查也只验证输出内部有序，**无法**发现"截断丢了更近的"——Java 侧修复后建议补一条"同 filter 两个 range 的小 range 命中必含于大 range 截断结果"的回归断言
